## 0. 先背这一段：60 秒版本

> 我给 AgentHub 做了一套会话级的长期记忆系统。Agent 每轮回复结束后，异步让 LLM 提取出五类结构化记忆存进 SQLite，写入是完全同步的本地操作，不做任何网络调用。
>
> 检索是 **BM25 + 向量双路召回，用 RRF 按名次融合**。做双路是因为两类查询各有所长：错误码、文件路径、变量名这类 token 在 embedding 词表里语义稀薄，向量路基本失效，而 BM25 是精确匹配；反过来同义改写的自然语言查询，BM25 一个词都命中不了。
>
> 最关键的一个决策是**检索作用域排他 —— 只搜当前会话**。因为项目之间会给出互相矛盾的约定，A 项目用 tab、B 项目用 2 空格，两者都对。而「矛盾」和「相关」在向量空间里是分不出来的，只有作用域能分。如果不排他，agent 会拿着另一个项目的约定自信地回答，而且没有任何信号提示出错了。

讲到这里停住，等面试官问。**不要一口气把下面全倒出来。**

## 1. 「这个项目解决了什么问题？」

不要答「实现了记忆功能」。答**具体的失效场景**：

原来的系统有四个独立的失效，而且是叠加的：

| # | 失效 | 现象 |
|---|------|------|
| 1 | FTS5 的 `unicode61` 分词器不切分 CJK | 一句中文被当成**一个 token**，只有整句精确匹配才命中 → 中文基本检索不出来 |
| 2 | 查询构造错了 | 用户原文直塞 `MATCH`，FTS5 把空格分隔的词按 **AND** 处理 → 多词查询几乎必然返回空 |
| 3 | 单聊路径根本不注入记忆 | 只有编排器路径注入 → 1:1 聊天里记忆**只写不读** |
| 4 | `conversation_id` 恒为 NULL、检索也不按会话过滤 | 记忆没有归属，是一锅没分类的粥 |

用户的主观感受是「**它不是记不住，是根本没用上**」。修复必须四项一起做，少任何一项都还是不可用。

**加分点**：第 4 项的性质与前几项不同 —— 前三项是「查不到」（漏召回），第 4 项是「查错了」（**错误召回**）。漏召回时 agent 会说「我不记得」，用户立刻知道；错误召回时 agent 会自信地按另一个项目的约定行事，**没有任何信号**。后者更危险。

### 1.1 先定位清楚：这是什么类型的 RAG

简历上写的是「混合检索 RAG」。**定位必须说准，否则第一个追问就会跑偏。**

**是 RAG**：检索相关记忆 → 注入 LLM 上下文，这就是 retrieval-augmented generation。

**但不是「文档 RAG」，是「记忆 RAG」**：检索对象不是原始文档切片，而是 **LLM 已经提炼过的原子事实**（「用户偏好 tab 缩进」）。这个区别决定了下面这张表 —— RAG 的标准追问在这套系统里各自的答案：

| RAG 标准问题 | 本系统的答案 | 状态 |
|---|---|---|
| 文档怎么分块（chunking）？ | **不分块。** 记忆本身就是 LLM 提炼过的原子事实：短、自包含、语义单一，是 chunk 的理想形态。给已经提炼过的事实再切一刀只会破坏语义 | 有意为之，有理由 |
| 用什么 embedding 模型？ | `bge-m3`（1024 维、不需要 query 前缀、MIT）。备选 `Qwen3-Embedding-0.6B`（同尺寸中文更强） | **推理选型，没跑过真实模型** |
| 检索策略？ | 混合检索：BM25 + 向量双路，RRF 按名次融合 | 已实现且有测试 |
| 怎么评估检索质量？ | **没做。** 需要 golden set + 消融实验 | **空白** |
| 怎么防止无关注入 / 幻觉？ | `minSimilarity` 阈值（0.35，经验值）+ 会话作用域收窄候选集 | 机制有，参数没标定 |

**「不分块」这一行是加分点而不是坑** —— 它说明你知道 chunking 是为了什么，并且判断出这里不需要它。反过来，如果面试官问「你怎么切的」而你答「我没想过」，那才是灾难。

**最后两行必须如实说**，展开见 §9。---

## 2. 三个必答的「为什么」

### 2.1 为什么是混合检索，不是纯 FTS5 或纯向量？

两路覆盖**不同的查询形态**，不是冗余：

| 查询形态 | 更强的路 | 例子 |
|---|---|---|
| 同义改写、语义相近 | 向量 | 存「偏好 tab 缩进」，查「帮我写个格式化脚本」 |
| 中文自然语言 | 向量 | 「我之前说的那个代码风格」 |
| **错误码、文件路径、变量名** | **BM25** | 查 `E_CONN_RESET`、`workspacePath` |

第三行是关键：这类 token 在 embedding 模型的词表里被切成碎片，语义稀薄，向量路基本失效；而 BM25 是精确匹配。记忆类型里的 `fact`（API 端点、配置）和 `error_pattern`（错误码）正属于这一类。

**如果面试官追问「有没有数据支撑」—— 如实说没有**：
> 「这三条判断目前是基于推理，不是基于数据。要真正验证需要 golden set 和消融实验，那是下一步的事。我可以说清楚它为什么在原理上成立，但我没有测过它到底好多少。」

这样答比硬编一个数字强得多。

### 2.2 为什么用 RRF，不用加权求和？

两个理由，第二个才是真正的理由：

**表层理由：两路的分数不可比。** FTS5 的 `rank` 无上界（越小越相关），余弦相似度在 `[-1,1]`。加权求和就必须先归一化，而归一化是一个「改错了也不报错、只是排序悄悄变了」的地方。RRF **只用名次不用分数**，从根上绕开这个问题。

公式：`score = Σ 1 / (k + rank + 1)`，`k = 60` 是通行取值。

**深层理由（这句说出来会加分）：RRF 融合的是「榜单」，所以缺失的榜单天然就是空集，融合层不需要任何降级分支。**

- 某条记忆还没嵌入 → 它只出现在 BM25 榜单里，向量榜单没有它 → 照样有分
- 查询向量化失败 → 向量榜单为空 → 退化为纯 BM25
- 某一路抛错 → 捕获后视为空榜单

三种情况走**同一条代码路径**。如果当初选的是加权求和，这三种情况就各需要一个 if-else，而每一个分支都是可能出错的静默点。

**追问陷阱**：「为什么不调 `k`？」→「RRF 的卖点正是不需要调参，它只用名次。真要调优先级，我应该调别的（比如给 `importance` 或新近度加权），而不是动 `k`。」

### 2.3 为什么作用域要排他，而不是「本会话优先 + 全局兜底」？★最重要的一题

**这题答好了，整场面试的基调就定了。** 它考的不是技术，是**判断力**。

先给结论：**因为「矛盾」和「相关」在向量空间里无法区分，只有作用域能区分。**

展开：

1. 本系统的实际使用方式是「一个项目 = 一个会话」——用户重开窗口回到的是**同一个** Conversation。
2. 项目之间会**互相矛盾**且都成立：A 项目约定 tab 缩进，B 项目约定 2 空格。
3. 假设 B 项目的记忆是「本项目用 2 空格」。在 A 项目里问「缩进该用几个？」——这条记忆与查询的语义相似度**极高**（0.9+）。如果允许跨会话召回，它必然排第一。
4. 结果是 agent 注入了一个**错误且与 A 项目历史矛盾**的约定，且如 §1 所说，**没有任何信号**提示这是外来上下文。
5. 而「这条记忆来自哪个项目」这个信息，在向量里根本不存在 —— 它只存在于 `conversation_id` 这个字段上。**作用域是唯一能表达它的东西。**

**主动交代代价**（这一点很重要，说明你想过权衡而不是拍脑袋）：
> 「这个选择的代价是明确的、我接受的：真正的跨会话知识，比如『这个人喜欢简洁回答』这种用户级偏好，在项目会话里**永远不会被召回**。要恢复它需要另做一路作用域为用户级的检索，并且要解决『项目约定和用户偏好冲突时谁优先』—— 那会削弱项目记忆的自洽性，所以我先不做，等有评测能力判断它是否净收益为正再评估。」

**顺带一提 `agentId` 的处理**（显示你注意到了一致性）：
> 「我还把 `agentId` 从检索过滤条件降级成了记忆的元数据。因为 `listMessages` 已经把同一个会话里所有 agent 的历史共享了 —— 如果历史跨 agent 共享、记忆却只属于单个 agent，语义就自相矛盾。两者边界必须一致。」

## 3. 中文检索：一个可以讲成故事的 bug

**这是最容易讲出「技术深度」的一段，因为根因很反直觉。**

**现象**：中文查询基本返回空。

**根因**：FTS5 的 `unicode61` 分词器按 Unicode 字符边界切分，但它**不切分 CJK**。所以「用户偏好使用 tab 缩进」在索引里是**一个 token**。

**第一反应是错的**：我一开始想换 `trigram` 分词器。但 `trigram` 按 3-gram 切，中文里**2 字词是最常见的词长**（缩进、接口、性能、偏好、配置、路径、错误）——2 个字符 < 3，`MATCH '"缩进"'` 会**静默返回 0 行，不报错**。这是个更隐蔽的坑。

**正确解法：预分词（pre-segmentation）** —— 在**应用层**用 jieba 把中文切成词、用空格连接，再写入索引列；查询侧走**同一个**分词器，然后 OR 展开。

```
content      = "用户偏好使用 tab 缩进"      ← 原样，用于展示
content_seg  = "用户 偏好 使用 tab 缩进"    ← 分词后，用于索引
```

这样 `unicode61` 就能得到真正的词级 token。

**三个可以深挖的点**：

1. **为什么写入侧要算，不能放触发器里？** SQLite 触发器调用不了 JS 分词器。
2. **为什么 tags 也必须分词？** tag `代码风格` 在 `unicode61` 下是**一个** token，而查询「代码风格」被 jieba 切成 `["代码","风格"]` 后 OR 展开，两个词项都匹配不到那一个 token → **静默不命中**。写入与查询必须走同一套分词。
3. **容错性质（这条能体现思考）**：写入与查询走同一个 `Segmenter`。**即使分词分错了，只要两端错得一致，匹配依然成立** —— 所以分词精度不敏感。这是它相对于「精确词边界」方案的容错优势。

**为什么选 `jieba-wasm` 而不是更快的 `@node-rs/jieba`？**（这题很能体现你踩过坑）
> 「性能不是区分项 —— 分词发生在每次写入一条记忆、每次查询一次，0.03ms 相对一次 embedding 调用可以忽略。真正的区分项是 **API 的容错性**：`@node-rs/jieba` 的 `new Jieba()`（不传词典）会返回**全是单字**的合法数组且**不抛错**，成词 0/5。因为两端一致就仍能召回，这个错误只表现为『检索精度变差』，是最难排查的一类。`jieba-wasm` 开箱即用、默认词典完整，没有这个错法。」

**顺带讲那个「不报错的错误」的哲学**（可以升华整场面试）：
> 「这个项目里我反复遇到同一类缺陷：参数、配置、约束都存在，但**没有任何东西观察它是否生效**。我在这套系统里数出四个先例 —— `CREATE TABLE IF NOT EXISTS` 跳过结构变更、`conversation_id` 恒为 NULL 且从没被任何查询观察过、`userId` 是可选的而两个调用点都漏传、环境变量名写错导致用户配置的模型从未生效。**四个里有四个都是读代码发现的，不是跑测试发现的。** 所以我的测试策略专门针对这一类：对每一个新增的必填参数、每一个新增的配置项，都配一个『**缺失或错配时会失败**』的测试，而不是只测『给对了会成功』。」

## 4. 写入与读取的时序（为什么写入不嵌入）

**核心决策：`createMemory` 是完全同步的、不做任何网络调用。**

```
[Agent 回复完成] → 异步触发 LLM 提取（fire-and-forget）
    → createMemory（同步，微秒级）
        ├─ 触发器同步写 FTS5 索引      ⇒ BM25 路【立即可查】
        └─ memory_embeddings 无此行     ⇒ 【进入待嵌入队列】
    → 返回，不等待 embedding
[后台 worker，每 5s 一轮] → 批量嵌入 → 写入向量 ⇒ 向量路【秒级可查】
```

**为什么这样设计？**
1. **写入路径不因 embedding 而变慢或丢数据**。embedding 服务挂了，记忆照样存得下、BM25 照样查得到。
2. **两路索引的更新时机不同**（FTS 同步即时、向量异步秒级），这个窗口是**设计的一部分**，不是缺陷 —— RRF 天然处理：该记忆只出现在 BM25 榜单里，照样参与排序，**无需任何特殊分支**。

**「待嵌入」不需要状态列 —— 它就是「没有对应向量行」。** 这是个可以讲得很漂亮的点：
```sql
SELECT r.id, r.content FROM memory_records r
LEFT JOIN memory_embeddings e ON e.memory_id = r.id
WHERE e.memory_id IS NULL OR e.fingerprint != ?
```
队列就是这个 LEFT JOIN。好处是：没有状态机、没有能写错的 `status` 列、天然自愈（worker 崩了重启即可继续）、**换模型自动重新入队**。

**追问陷阱：「查询延迟呢？」** → 老实说：读路径新增了一次 embedding 网络调用，**100–300ms**，由它主导。**这是这个设计唯一新增的同步延迟**。但这个延迟有具体解法，不是理论上的：推荐落地路径就是**本地 Ollama**，同一套 OpenAI 兼容实现只改 `EMBEDDING_BASE_URL`，延迟降到毫秒级且不需要任何 API key。

## 5. 数据一致性与迁移

**「加了新列/换了索引结构，已有数据库怎么办？」**

原来 `initSchema()` 只有 `CREATE TABLE IF NOT EXISTS` —— 对已存在的库**静默跳过**任何结构变更。而换分词器必须 `DROP` 虚表并 `rebuild`，`IF NOT EXISTS` 做不到。结果是「看着修好了，其实没修」。

**解法：`PRAGMA user_version` 迁移框架**，每个迁移在事务内执行，失败整体回滚且版本号不推进。

版本划分：
- **v1** = 原有 schema（对老库是 no-op，对新库是建库）—— 这样老库和新库走**同一条路径**，不需要分支
- **v2** = 加 `content_seg`/`tags_seg` 两列 + 建 `memory_embeddings`
- **v3** = 把 FTS 虚表重建到分词列上

**一个必须讲到的坑**（能体现你真的跑过）：
> 「v3 把 FTS 虚表指向了新的分词列，但**迁移完成到第一次 `rebuild` 之间有一个窗口**：索引是空的，而 `memory_fts` 有数据。这个窗口内 BM25 的 `MATCH` 会**静默返回 0 行**，而 RRF 会把『索引故障』当成『没有匹配』。
>
> 更麻烦的是，外部内容表的 FTS 虚表在 `DROP`/`CREATE` 之后、`rebuild` 之前，对**已存在的行**执行 `UPDATE`/`DELETE` 会抛 `SQLITE_CORRUPT_VTAB`。所以直觉的顺序（先回填、再 rebuild）在**老库上必然失败**。正确做法是先 `rebuild`，或者在回填期间把触发器摘掉再装回去 —— 我把整个 DROP → 回填 → rebuild → 恢复触发器放在**同一个事务**里，异常既不会丢触发器也不会重复创建。」

**为什么要有「索引未就绪」标志？** `bm25Ready === false` 时 BM25 路**跳过并打 warning**，而不是执行 `MATCH` 返回空榜单。因为「BM25 没有匹配」和「BM25 不可用」在 RRF 里表现完全相同（都是空榜单），但语义完全不同 —— 前者是正常结果，后者是故障。**用一个显式标志把两者分开，故障才不会被当成正常结果吞掉。**

## 6. 安全边界：跨租户泄漏

**这是被问到时必须能立刻答上来的一条。**

**原有的问题**：检索只按 `agentId` 过滤，**没有 `userId`**。而 `Agent = Contact`，用户可以通过导入别人发布的 Agent 得到**自己的** Contact 行 —— 正常情况下两个用户的 `agentId` 不同，但只要出现任何一种 agentId 复用（同一 Contact 被共享、数据导入、测试夹具、未来的团队共享），**A 的记忆就会被召回到 B 的提示词里**。

**为什么没人发现**：`userId` 参数是**可选的**，而唯一的两个自动化调用点都漏了它。单用户场景下测试全绿，结果完全正确。

**处理方式（有设计感的一点）**：把 `userId` 和 `conversationId` 一并改成**必填的判别联合类型**，让漏传成为**编译错误**：

```typescript
type MemoryScope =
  | { conversationId: string }    // 会话内 —— 所有自动检索链路
  | { allConversations: true };   // 全库 —— 仅 Web UI 手动搜索
```

**为什么不用 `conversationId?: string` 可选参数？** 因为可选参数有一个**已经发生过一次**的失效方式：`userId` 就是可选的，两个调用点都漏了，而且单用户测试全绿。判别联合让「跳过会话过滤」成为**必须显式写出的决定** —— 漏写 `scope` 是编译错误；写错则需要主动打出 `allConversations: true`，无法因疏忽而跨会话。

**追问陷阱：「向量那一路呢？它也能过滤吗？」** → 老实说这个坑很深，而且是个能加分的诚实回答：
> 「`VectorIndex.search` 的 filter 签名在设计里被冻结成了 `{userId, scope}`。但我在整分支复审时发现，`agentId` 这个**展示层筛选**一开始只加在了 BM25 那一路 —— 于是 `?agentId=X` 的搜索会返回另一个 agent 的、但语义可召回的向量命中。冻结的接口挡不住这个，因为 `searchMemories` 这一层保留 `agentId` 正是为了这个筛选。修法是把 `agentId` 挪到融合之后**只做一次**，而不是各写一份。
>
> 这里还有个更微妙的教训：我们的融合后过滤**会掩盖**腿级别的过滤失效 —— 也就是说，就算某一路的 scope 过滤被删掉，端到端的隔离测试**照样通过**。所以我专门写了一个测试去探测每一路的**输入**（向量路收到的 filter 对象、BM25 实际执行的 `MATCH` SQL），而不是只看最终结果。」

## 7. 面试官常见的连环追问（速查）

| 追问 | 答案要点 |
|---|---|
| 为什么不用 Qdrant / Chroma？ | 违背仓库「无需数据库容器」原则；而且单会话预期记忆量在**数百到数千条**，暴力扫描是微秒级 |
| 为什么不用 sqlite-vec？ | `vec0` 至今仍是**暴力精确 KNN**（O(N) 全扫），`rescore` 只是常数因子优化，没有 HNSW/IVF 那类亚线性结构。它相对 JS 暴力的唯一实质优势是 C 层 SIMD，而这个优势要到**五万条以上**才显现。为此引入平台原生二进制不划算 |
| 为什么不分块（chunking）？ | 长期记忆是 LLM 提炼过的**原子事实**（「用户偏好使用 tab 缩进」），本身就是 chunk 的理想形态：短、自包含、语义单一。给已经提炼过的事实再切一刀只会破坏语义 |
| 为什么把 `memory.db` 和业务库分开？ | `prisma db push` 不认识 FTS5 的影子表（`memory_fts_*`），会把它当 schema drift 删掉，丢索引 |
| 向量怎么存的？ | 归一化后的 `Float32Array` 原始字节存 BLOB。**归一化后余弦相似度等于点积**，距离计算退化成一重循环，省掉每对向量两次开方 |
| 怎么保证向量和查询在同一个空间？ | `fingerprint = ${model}:${dim}:${mode}:${prefixDigest}` 是失效判据。**只用 `model` 不够** —— Qwen3-Embedding 同一个模型名可以服务多个输出维度，只比 `model` 会让不同维度的向量混进同一个索引，点积照算不误、结果全错且无异常 |
| `dim` 只声明不校验行不行？ | 不行，这是一个**静默数据损坏点**：BLOB 读取是 `new Float32Array(buf, off, dim)`，`dim` 直接决定解析多少个 float32。配 1024 而端点返回 1536 → 写入正常、读取静默截断 → 表现为「语义召回不太准」而不是像 bug |
| 为什么拒绝 NaN 向量？ | 这不是通用健壮性加固，是 `bge-m3` + Ollama 的**已知缺陷**（issue #14657，对某些技术文档返回 NaN），而本项目存的正是技术文档。NaN 会一路静默通过：长度校验通过、归一化 `NaN/NaN=NaN` 不抛错、BLOB 存得下、点积传播、**`sort` 比较返回 `false` 导致排序结果任意且不报错** |
| 怎么防止 embedding 服务挂掉影响使用？ | 写入完全不受影响；检索退化为纯 BM25；worker 下轮重试。另外读路径的 HTTP 调用**设了 5s 超时** —— 否则端点接受连接后不返回会把读路径挂住几分钟，现象是 agent 从此不再回复 |
| 怎么保证配置被真正读取？ | **不给默认值**。四个 `EMBEDDING_*` 变量缺任意一个，整块配置就是 `undefined`，启动打一条 warning 并退化为纯 BM25。这是从一个**正在发生的 bug** 学来的：`.env` 里写 `MODEL=`，代码读的是 `LLM_MODEL`，`?? "deepseek-chat"` 静默兜底 → 用户配置的模型**从未生效**且没人发现。**没有兜底时，「配置错误」等价于「启动失败」，这是唯一能保证配置被真正读取的机制。** |

## 8. 深水区（答得出来是加分）

- **为什么 `searchMemories` 必须异步？** 它内部需要一次 embedding API 调用把 query 变成向量，这是 I/O。注意：真正 fire-and-forget 的是**写入**路径；检索仍然是阻塞等结果后拼接的。
- **`minSimilarity` 为什么是必须的？** 暴力搜索对**任意**查询都会返回 top-k（哪怕相似度只有 0.1，它总会给出最近的 k 条），RRF 照样融合 → prompt 被无关记忆污染。**注入低相关记忆比不注入更糟**：浪费 token，且可能让 agent 产生错误确信。在会话作用域下这个风险**更大而不是更小** —— 候选集小了，更容易「凑够」k 条无关记忆。
- **`update` 为什么不能用 `delete + create`？** 会让 `id` 变更（`sourceMessageId` 溯源链断裂）、`created_at` 被重置（丢失记忆年龄）、向量行成孤儿。而且内容变更时必须**删掉该 id 的向量行**让它重新入队 —— 因为失效判据是 `model:dim:mode`，它**检测不出内容变化**。
- **为什么 BM25 路也要 `ORDER BY rank LIMIT 50`？** 两路各取 top-50 作为融合输入，融合后取 `limit`。截断策略是设计的一部分，我也知道它有边界（`offset` 超出候选池会返回空）—— 这是已知限制。
- **`importance` 字段有什么用？** 目前只存储与展示，**没有参与排序加权**。给 `importance`/新近度加权属于需要评测数据支撑的调参，我留到有 golden set 之后。

## 9. ★ 已知限制与如何诚实回答（必读）

**这一节比前面所有节都重要。** 面试官最容易被激怒的不是「你没做」，而是「你把自己没做的事说成做了」。下面每一条都准备好**如实说**，而且**主动说**——主动交代限制会显著提高可信度。

### 9.1 没有用真实的 embedding 模型跑过端到端

**这是最大的一个空白。** 所有测试都用假的 embedding provider（不依赖真实模型、不依赖网络，这是刻意的设计约束），而真实的 `bge-m3` + Ollama 验收步骤**没有在本机执行过**——因为没有可用的 embedding 端点。

**怎么答**：
> 「功能层面我是按真实端点写的，用 OpenAI 兼容协议，测试全部注入假的 provider 以保证不依赖网络。但**真实的 `bge-m3` + Ollama 端到端我没跑过**，因为本地没有部署。这是最大的一条未验证项，我在文档里也写明了。」

**如果被追问「那你凭什么说它能用？」** → 区分**已验证**和**未验证**：
- 已验证：迁移链（用真实的老库结构跑过 v0→v3，200 行数据回填正确）、作用域隔离（两条路都断言）、中文 2 字词召回（真实 FTS5 表上跑 `MATCH`）、索引未就绪窗口、降级路径。
- 未验证：真实模型返回的向量质量、端到端延迟、`bge-m3` 在本项目文档类型上的实际行为。

### 9.2 `bge-m3` + Ollama 有一个已知缺陷，且正好命中本项目的文档类型

Ollama issue #14657：`bge-m3` 对**某些技术文档**返回 NaN 向量。本项目存的就是错误码、文件路径、API 端点、配置片段。

**怎么答**：先说**你怎么防的**（`isFinite` 校验 + 丢弃 + 下轮重试，表现为「该条记忆暂时只在 BM25 榜单里」），再说**防住了不等于没损失**：
> 「挡得住不等于没有损失 —— 那些记忆会永久停留在『只有 BM25 可召回』的状态。我把它记成了需要观察的项：如果待嵌入计数长期不降，就说明这个缺陷在频繁触发，那时应该换模型或换推理后端。**这是选 Ollama + bge-m3 这个具体组合的代价，不是通用风险。**」

### 9.3 所有阈值都是拍的经验值，没有实验支撑

| 参数 | 值 | 状态 |
|---|---|---|
| `minSimilarity` | 0.35 | **拍的经验值**，spec 明确写了「具体取值留给后续用消融实验标定」 |
| RRF `k` | 60 | 通行取值，**没调过参** |
| 每路候选数 | 50 | 拍的 |
| 检索引擎注入的 token 预算 | 800 | 拍的；且字符估算对纯中文**低估约 4 倍** |
| 每条记忆的重要性范围 | 1–10 | LLM 自评，**没有参与排序** |
| 重建超时 | 30s | 拍的，而且**实际上约束不了耗时**（重建是同步的，抢不了跑） |

**怎么答**：
> 「这些数字我都可以告诉你出处：RRF 的 `k=60` 是论文和业界的通行值；其余几个是拍的经验值。**真正诚实的说法是：我用数据标定过的参数是零个。** 混合检索比纯 BM25 到底好多少、`minSimilarity` 该取多少，都需要 golden set 和消融实验 —— 那是下一阶段的事，我现在能讲清楚的是**机制为什么成立**，不是**参数为什么是这些值**。」

### 9.4 「漏传参数是编译错误」这个保证在当前仓库里是名义上的

设计的核心安全网是「漏传 `userId`/`scope` 必须是编译错误」。但仓库的 lint 门禁**本来就是红的**（一堆既有的类型错误），而且打包器不做类型检查。

**怎么答**：
> 「设计上我用必填的判别联合把它变成编译错误。但要诚实说：这个保证在当前仓库里**没有被强制** —— 我们的 `tsc --noEmit` 门禁本来就是红的，所以一个漏传 `scope` 的改动不会让构建失败，只会让错误淹没在既有的错误里。**这是一个我知道、但还没修的基础设施问题**：要真正兜住，需要让依赖这些契约的包有一个干净的类型检查门禁。」

### 9.5 明确没做的（都有理由，被问到要能说出理由）

| 没做 | 理由 |
|---|---|
| 跨会话的用户级偏好召回 | 与排他作用域直接冲突。需要另做一路并解决冲突消解，先做排他、待评测能力就位后再评估放宽 |
| 记忆的衰减 / TTL / 遗忘 | 需要评估数据支撑 |
| 检索质量评测（golden set、消融） | 是独立的一期工作，本设计落地后才有东西可测 |
| 把「项目」抽象成独立实体 | 当前 `Conversation` 事实上充当了项目；新增 `Project` 模型在约定被打破之前没有收益 |
| Web UI 的记忆面板 | 与检索质量正交 |
| 向量库外部化 | 违背「无需数据库容器」原则 |
| 分块（chunking） | 见 §7 |
| 多实例横向扩展 | SQLite 是单写者，本设计不改变该约束 |

### 9.6 一个已知的跨库一致性问题

删除会话**不会**清理记忆 —— 记忆库和业务库是**两个独立的 SQLite 文件**，跨文件建不了外键。后果是孤儿记忆行累积（但它们本来也不可召回，因为作用域排他）。**我做的是让它可观测**：`/api/memory/list` 会返回 `orphanCount`。

## 10. 不要说的话

| ❌ 不要说 | 为什么 |
|---|---|
| 「跨会话记忆」/「让 Agent 记住用户偏好」 | **这是本设计明确排除的东西**，而且你简历上原来就是这么写的。作用域是**会话级**、排他的。说错了会被追着打 |
| 「我做了消融实验 / 评测」 | 没做 |
| 任何没测过的性能数字（QPS、延迟降低 X%、召回率 Y%） | 你只有一个「100–300ms 是远程端点的理论延迟」这个量级判断，没有实测 |
| 「生产环境验证过」 | 没有。真实模型端到端都没跑过 |
| 「用的向量数据库」 | 不是向量库，是 SQLite BLOB + JS 暴力余弦 |
| 「我实现了一套 RAG 框架」 | 这是一个模块，不是框架 |
| 「完美解决了中文分词」 | 是**用预分词绕开了 FTS5 的分词能力缺失**，且分词精度本身不敏感（两端一致即可），不是「解决了分词问题」 |

**如果某个问题你确实不知道** —— 直接说「这块我没深入，我知道的是……」比编一个答案安全得多。技术面试官几乎都能听出编造。
