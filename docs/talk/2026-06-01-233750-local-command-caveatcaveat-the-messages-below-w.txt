● 好的，现在我对所有三个 bug 的根因有了完整清晰的认识。以下是我的分析：

  ---
  三个 Bug 的深入分析

  Bug 1：群聊 @两个 agent 只有一个响应 + 命令行闪烁

  一个 agent 不响应的根因： 有两个可能，且很可能同时存在：

  原因 A — LLM Intent Analyzer 没有正确分配两个 agent

  apps/server/src/orchestrator/intent-analyzer.ts 中，@mention 的解析依赖外部
  LLM：
  "If the user @mentions an agent name or role, find the matching agent ID from
  the list above"

  如果外部 LLM（DeepSeek）只识别出一个 agent 并只返回一个 assignedAgent，另一个
  agent 就不会被分配到任务。而且 LLM 调用有 15 秒超时（timeout: 
  15000），如果超时则 fallback 到 ALL agents，但如果 LLM
  在超时前返回了错误的结果（只识别出一个），就不会走 fallback 路径。

  原因 B — 前端只有一个 streamingMessage，两个 agent 的 SSE chunk 互相覆盖

  前端 chat-context.tsx 的 appendMessageChunk 只维护一个 StreamingMessage
  对象。当两个 agent 并行执行时，它们的 chunk SSE
  事件交替到达，内容全部追加到同一个 streamingMessage.content 里：

  AgentA: "我在分析..."  → content = "我在分析..."
  AgentB: "我来处理..."  → content = "我在分析...我来处理..."
  AgentA: "找到问题了"  → content = "我在分析...我来处理...找到问题了"

  当第一个 agent 完成发送 done 事件 → finalizeMessage() 清除
  streamingMessage，第二个 agent 后续的 chunk 可能创建新的 streaming
  但立刻又丢失。

  而且 dispatcher.ts 第106行中 onTaskCompleted 没有 await：
  onTaskCompleted?.(sub, settled.value);  // ← 没有 await，fire-and-forget
  pushSSE("done", { ... });
  这样即使 onTaskCompleted 中的 DB 写入失败了，done 事件也会继续发送。

  命令行闪烁的根因：

  在 claude.adapter.ts 第119行，spawn() 在 Windows 上默认会打开控制台窗口。虽然
  resolve-cli.ts 尝试将 .cmd 文件解析为直接可执行的 .js/.exe，但 spawn()
  调用时没有设置 windowsHide: true：

  this.process = spawn(resolved.command, [...resolved.prefixArgs, ...args], {
    stdio: ["pipe", "pipe", "pipe"],
    cwd: this.config.cwd,
    env,
    // 缺少 windowsHide: true
  });

  每次 agent 执行都 spawn 一个 CLI 子进程（Claude 或 OpenCode），导致 cmd
  窗口弹出又关闭。

  Bug 2：Agent 输出未存入数据库

  根因：数据保存了，但前端在 done 事件中拿不到真正的 messageId

  追踪完整链路：

  1. dispatcher.ts 第106行调用 onTaskCompleted 保存消息到 DB
  ✅（消息确实保存了）
  2. 第108行发送 done 事件：
  pushSSE("done", {
    messageId: "",   // ← 空字符串！
    tokenUsage: ...,
    agentId: sub.agentId,
  });
  3. 前端 useSSEStream.ts 收到 done 事件：
  finalizeMessage(data.messageId, data.agentId);  // messageId = ""
  4. 前端 chat-context.tsx 的 finalizeMessage：
  const id = messageId || prev.id;  // 由于 messageId=""，使用 prev.id = 
  "streaming-N"
  5. 前端再次加载消息列表时，由于 messageId 是临时的
  "streaming-N"，不会与后端真正的消息 ID 匹配

  所以消息确实写入了数据库（DB 中有记录），但前端 UI 
  在刷新页面后看不到这条消息，因为：
  - 前端显示的 streaming-N ID 是假的
  - 当用户切换会话再回来时，消息列表重新从 API 加载，前端用 streaming-N 去 match
   后端的真实 ID，match 不上 → 会作为新消息添加

  这就给用户造成了"没有保存到数据库"的错觉。实际上保存了，但前端的 messageId
  映射断了。

  Bug 3：HTML 输出没有渲染成 iframe

  根因：整个 HTML → web_preview artifact 的链路完全缺失

  从 agent 输出到前端展示的链路：

  - RightPanel.tsx 第122行：同样只在 artifact.type === "web_preview" 时触发

  你给出的例子是 Claude 的 TodoWrite 工具调用 — 它被解析为 ToolCall
  chunk，最终渲染为文本。

❯ HTML → iframe 渲染这块，这三种方案有什么区别？我现在只看懂了客户端检测        

● 好，我拿具体例子来说明三个方案的本质区别。

  ---
  方案详解

  先看当前链路：

  Agent 输出: "<html><body><h1>Hello</h1></body></html>"
    → chunk parser 生成: { type: "Text", content: "<html>..." }
    → 服务器: 存为 Text 消息，content = "<html>..."
    → 前端 MarkdownRenderer: 把它当普通文本渲染
    → 用户看到: <html><body><h1>Hello</h1></body></html>   ← 就是一段文本/代码

  方案 B — 客户端检测（你已理解）

  Agent 输出同上
    → 服务器照常处理，存为 Text 消息
    → 前端 MarkdownRenderer(或外层 wrapper)检查 content:
        "开头是 <html>？或者包含 <div>、<iframe> 等标签？"
    → 是HTML → 不经过 react-markdown，直接渲染：
        <iframe srcdoc={content} sandbox="allow-scripts" />
    → 用户看到: 一个嵌入式页面，显示 "Hello"

  本质：纯前端行为，后端根本不知道发生了 HTML 转换。

  方案 A — 服务端检测

  Agent 输出同上
    → chunk parser 照常解析，streaming 照常推
    → 服务器在 agent 完成后拿 fullResponse 检查:
        "这段文本是 HTML 吗？"
    → 是HTML → 额外创建一条 artifact 记录:
        createArtifact({
          messageId: saved.id,
          type: "WebPreview",     // ← 数据库字段
          content: fullResponse,   // ← 存原始 HTML
        })
    → 前端拿到消息数据时，同时看到:
        - 消息: { type: "Text", content: "<html>..." }
        - artifact: { type: "web_preview", content: "<html>..." }
    → RightPanel/ArtifactCard 的已有 iframe 逻辑渲染它

  本质：后端多写一条 artifact 记录，前端复现已有的 iframe 渲染能力。

  方案 C — ToolCall 钩子

  Agent 执行过程中产生:
    { type: "ToolCall", name: "TodoWrite", input: "..." }
    ↓
  服务器在 pushChunk 阶段拦截:
    "这是一个 ToolCall，name 是 TodoWrite → 生成 artifact"
    ↓
    createArtifact({ type: "WebPreview", content: ... })
    pushSSE("artifact_status", { id, status: "completed", title })
    ↓
  前端收到 artifact_status 事件 → 显示 ArtifactCard → iframe

  同时该 ToolCall 的文本仍然正常渲染在消息里。

  本质：不检测最终内容，而是根据工具调用的类型决定是否创建 artifact。

  ---

  function sniffArtifactType(content: string): "web_preview" | "diff" | 
  "document" | null {
    const s = content.trim();

    // HTML detection
    if (
      s.startsWith("<html") ||
      s.startsWith("<!DOCTYPE html") ||
      s.startsWith("<!doctype html") ||
      s.startsWith("<svg") ||
      (s.startsWith("<") && /^<\w+[\s>]/.test(s) && /<\/\w+>\s*$/.test(s))
    ) {
      return "web_preview";
    }

    // Diff detection
    if (s.startsWith("diff --git") || s.startsWith("--- a/")) {
      return "diff";
    }

    // None of the above
    return null;
  }
