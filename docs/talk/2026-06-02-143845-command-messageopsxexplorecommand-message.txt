  第 8 模块：Orchestrator（多 Agent 任务编排器）— 详细实现计划

  概述

  Orchestrator 是整个平台的"大脑"——当用户在群聊中发送消息并 @ 提及多个 Agent

    async dispatchParallel(subtasks: SubTask[]): Promise<Map<string,
  SubTaskResult>> {

      // 2. 每个子任务使用独立的 SSE 事件通道（event: agent:${agentId}:chunk）
      // 3. 等待所有并行任务完成（Promise.allSettled）
      // 4. 返回每个子任务的结果
    }

    private async executeSubTask(subtask: SubTask): Promise<SubTaskResult> {
      // 1. 创建 AgentAdapter（通过 createAdapter）
      // 2. 构建 AgentContext
      // 3. 遍历 AsyncIterable<Chunk>
      // 4. 每个 Chunk 通过 connectionManager.pushToConversation() 推 SSE
      // 5. 收集完整结果
    }
  }

  任务 8.4：失败处理

  目标：Agent 失败时重试一次，仍失败则跳过并继续执行其他任务。

  策略：

  失败处理流程:

  子任务执行失败
      │
      ├── retryCount === 0? ──→ 重试一次（重新创建 adapter，再次 execute）
      │                              │
      │                              ├── 成功 → 标记 completed
      │                              └── 失败 → 标记 failed
      │
      └── retryCount >= 1? ──→ 标记 failed/skipped
                                    │
                                    ▼
                              依赖方处理:
                              - 如果下游任务标记了 `continuesOnFail: true` →
  继续执行（下游拿到空结果）
                              - 否则 → 下游任务标记为 skipped

  // executor.ts

  export class SubTaskExecutor {
    private readonly MAX_RETRIES = 1;

    async executeWithRetry(
      subtask: SubTask,
      adapter: AgentAdapter,
      onChunk: (chunk: Chunk) => void,
    ): Promise<SubTaskResult> {
      for (let attempt = 0; attempt <= this.MAX_RETRIES; attempt++) {
        try {
          const context = this.buildContext(subtask);
          const chunks: Chunk[] = [];

          for await (const chunk of adapter.execute(context)) {
            chunks.push(chunk);
            onChunk(chunk);  // 实时推 SSE
          }

          return { success: true, chunks };
        } catch (error) {
          if (attempt < this.MAX_RETRIES) {
            // 重试：重新创建 adapter（清理旧连接）
            adapter.abort();
            adapter = this.createAdapter(subtask);
            continue;
          }
          // 最终失败
          return { success: false, error: formatError(error) };
        }
      }
    }
  }

  对并行任务的影响：
  - Promise.allSettled 确保一个失败不影响其他并行任务
  - 失败的任务在聚合时标记，下游任务根据依赖类型决定是否继续

  Dispatcher 中嵌入事件推送

  // dispatcher.ts — 调度过程中同时发状态事件

  async dispatchAll(decomposition: TaskDecomposition): Promise<void> {
    // 1. 先发送完整的任务结构
    this.pushEvent("orchestrator:decomposition", {
      subtasks: decomposition.subtasks.map(s => ({
        id: s.id, agentName: s.agentName,
        instruction: s.instruction, dependsOn: s.dependsOn,
      })),
      layers: decomposition.layers,
    });

    // 2. 逐层执行，每层内并行
    for (const [layerIndex, layer] of decomposition.layers.entries()) {
      const tasks = layer.map(id => decomposition.subtaskMap.get(id)!);

      // 发送这一层每个任务的状态: running
      for (const task of tasks) {
        this.pushEvent("orchestrator:task-status", {
          subtaskId: task.id, status: "running",
          agentName: task.agentName, layer: layerIndex,
        });
      }

      const results = await this.executeLayer(tasks);

      // 发送每个任务的结果状态
      for (const [id, result] of results) {
        this.pushEvent("orchestrator:task-status", {
          subtaskId: id,
          status: result.success ? "completed" : "failed",
          agentName: decomposition.subtaskMap.get(id)!.agentName,
          layer: layerIndex,
          error: result.error,
        });
      }
    }

    // 3. 发送聚合结果
    this.pushEvent("orchestrator:aggregated", { summary, total, completed,
  failed });
  }

❯ layers: string[][];这个是用来干什么的？                                       

● layers 是 DAG 拓扑排序的结果，用来表达哪些任务可以同时执行。

  什么意思

  假设我们有这样的依赖关系：

  T1 (无依赖)
    │
    ├──→ T2 (依赖 T1)
    │
  T3 (无依赖) ──→ T4 (依赖 T3) ──→ T5 (依赖 T4)

  拓扑排序后分层：

  layers = [
    ["T1", "T3"],    // 第 0 层：T1 和 T3 都没有依赖 → 可以同时跑
    ["T2", "T4"],    // 第 1 层：T2 等 T1，T4 等 T3 → 可以同时跑
    ["T5"],          // 第 2 层：T5 只能等 T4 完成
  ]

  为什么设计成 string[][] 而不是用其他结构

  其实就是每层是一个 string[]（该层所有任务的 ID），多层组成 string[][]。原因：

  对于调度器（dispatcher）：

  for (const layer of layers) {
    // 一层内的任务全部并行启动，Promise.allSettled 等全部完成
    const results = await Promise.allSettled(
      layer.map(taskId => executeTask(taskId))
    );
    // 下一层开始...
  }

  代码就是一个简单的两层循环——外层串行走层，内层并行走任务。不需要递归、不需要遍
  历图。

  对于前端：

  示例: layers = [["T1","T3"], ["T2","T4"], ["T5"]]

  前端渲染:
    ┌─ 第1轮 ─────────────────┐
    │ ⬜ T1: 产品需求分析       │  ← 并行
    │ ⬜ T3: 竞品调研           │
    └──────────────────────────┘
         ↓ T1完成，T3完成
    ┌─ 第2轮 ─────────────────┐
    │ ⬜ T2: 设计方案           │  ← 并行
    │ ⬜ T4: 输出调研报告       │
    └──────────────────────────┘
         ↓ T2完成，T4完成
    ┌─ 第3轮 ─────────────────┐
    │ ⬜ T5: 最终方案评审       │  ← 串行
    └──────────────────────────┘

  前端拿到 layers 后，可以：
  - 按轮次渲染进度，用户知道现在是"第 2/3 轮"
  - 同一轮的任务用相同缩进/分组样式
  - 直观显示整体完成度：(当前轮 / 总轮数)

  可以有其他表达方式吗？

  当然，比如每个 SubTask 自己带一个 layer: number 字段，前端自己去分组：

  [
    { id: "T1", layer: 0, dependsOn: [] },
    { id: "T3", layer: 0, dependsOn: [] },
    { id: "T2", layer: 1, dependsOn: ["T1"] },
    ...
  ]

  这跟 layers: string[][] 是等价信息，但 layers
  作为独立的数组在前端渲染时可以直接按 map
  遍历，前端不需要自己算拓扑排序——编排器算好了直接给前端。

  ---
  总结：layers 就是调度引擎产出的执行计划，同时给后端调度器和前端渲染用，两端共
  享同一个"执行时间表"。
