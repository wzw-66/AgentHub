  关键洞察

  1. 混合检索（语义+关键词+时间+实体关联）是标配 — RRF融合在 Benchmark
  上系统性最佳
  2. 2025年最大反转：纯 SQLite FTS5 打败了向量库 — OpenDB
  零嵌入模型达到93.6%，证明对于很多场景，传统全文索引就够了
  3. "保留原始数据"趋势 — MemMachine 指出 LLM
  提取是有损的，直接存原始片段反而更好
  4. MCP 是标准接口 — 几乎所有项目都提供 MCP Server 集成
  5. Letta 的惊人发现 —
  用最普通的文件系统工具（grep/search_files）跑分超过了专用记忆工具

  现有系统集成分析

  目前 AgentHub 已有的记忆相关能力：
  - 对话消息历史（Message 表）— 会话级短期记忆
  - Pinned Messages（已实现 pin 功能）— 人工选择的"重要记忆"
  - 无长期结构化记忆 — Agent 每次调用只有当前对话上下文

  要在 AgentHub 中加长期记忆，需要：
  1. 记忆存储层 — 持久化记忆的结构化存储
  2. 记忆提取层 — 从对话中自动提取关键信息
  3. 记忆检索层 — 在 Agent 执行前注入相关记忆
  4. 记忆管理层 — 更新、衰减、冲突解决、合并

  在选模式之前，先看 实现路径方案：

  方案 A：纯 SQLite 路线（推荐）

  - Summary: 基于 better-sqlite3 + SQLite FTS5 全文索引，在 @agenthub/memory
  新包中实现，零外部依赖
  - Effort: 人 ~3天 / CC ~1小时
  - Risk: Low — SQLite 非常成熟，FTS5 内置于 SQLite 中
  - Pros:
    - ✅ 零额外基础设施（不需要向量库、嵌入服务、图数据库）
    - ✅ OpenDB 已证明此方案在 Agent 记忆场景达到 93.6% 精度
    - ✅ 1ms 级延迟，极低资源消耗
    - ✅ 与 Prisma/PostgreSQL 正交，互不影响
  - Cons:
    - ❌ 不支持语义相似度搜索（需要用关键词+标签模拟）
    - ❌ 没有图关系推理能力

  方案 B：向量嵌入路线

  - Summary: 使用 sqlite-vec 或 pgvector 在 PostgreSQL 中做向量存储，集成
  @xenova/transformers 做本地嵌入
  - Effort: 人 ~5天 / CC ~2小时
  - Risk: Med — 引入新依赖，嵌入模型运行在服务端增加 CPU/内存开销
  - Pros:
    - ✅ 支持语义搜索 — "帮我找上次聊的那个关于认证的东西"也能搜到
    - ✅ 与现有 PostgreSQL 数据库统一部署
  - Cons:
    - ❌ 嵌入模型增加 100-500MB 依赖大小
    - ❌ CPU 推理嵌入速度慢（GPU 版本增加运维复杂度）
    - ❌ 冷启动问题 — 新领域数据嵌入质量差

  方案 C：混合路线（推荐）

  - Summary: 先用 SQLite FTS5
  做基础存储和关键词检索，预留向量嵌入接口作为可选增强层
  - Effort: 人 ~4天 / CC ~1.5小时
  - Risk: Low-Med — 略复杂于纯 SQLite，但留有增长空间
  - Pros:
    - ✅ 核心功能零依赖，立即可用
    - ✅ 向量层可选 — 用户安装额外依赖就能启用语义搜索
    - ✅ 覆盖最全场景：关键词精确匹配 + 可选语义模糊匹配
    - ✅ 渐进式 — 初期跑 SQLite FTS5，后期按需引入向量
  - Cons:
    - ❌ 架构略复杂，需要设计好抽象层

  RECOMMENDATION: 方案 C（混合路线）—— 核心零依赖，向量作为可选增强。AgentHub
  当前是多人协同 IM 场景，关键词+标签+时间范围检索已经能覆盖 90%
  的需求。给未来留了语义搜索的扩展点但不绑架。

  ---
  Step 0A — Premise Challenge

  1. 这是正确的问题吗？

  是。AgentHub 的核心价值是"多AI Agent 协作"，但当前 Agent 在每次交互中都是
  stateless — 它们只能看到当前对话的消息历史。这意味着：
  - 同一个 Agent 在不同对话中不能记住用户偏好
  - 跨会话的上下文（用户项目结构、常用技术栈、历史决策）完全丢失
  - Agent 无法从过去错误中学习

  长期记忆是从"多Agent聊天工具"进化到"真正智能的AI协作平台"的必要条件。

  2. 不做会怎样？

  AgentHub 会停留在"一个漂亮的聊天界面"而非"AI 同事"。用户的 Agent
  不会随着时间变聪明，每次交互都是从头开始。

  3. 更直接的路径？

  RAG 是最直接的替代方案 — 但这需要用户额外搭建知识库。AgentHub
  的长期记忆应该是自动积累的，从对话中无痛沉淀，不需要用户手动"喂文档"。

  数据模型 (SQLite FTS5)

  -- 核心记忆表
  CREATE TABLE IF NOT EXISTS memory_records (
    id         TEXT    PRIMARY KEY,
    user_id    TEXT    NOT NULL,     -- 所属用户
    agent_id   TEXT    NOT NULL,     -- 所属 Agent (Contact.id)
    type       TEXT    NOT NULL DEFAULT 'fact',
    content    TEXT    NOT NULL,     -- 记忆内容
    tags       TEXT    NOT NULL DEFAULT '[]',  -- JSON 标签数组
    source_message_id TEXT,          -- 来源消息 ID
    conversation_id   TEXT,          -- 来源会话 ID
    importance INTEGER NOT NULL DEFAULT 1,  -- 1-10 重要性
    created_at TEXT    NOT NULL,
    updated_at TEXT    NOT NULL
  );

  -- FTS5 全文索引 (content + tags 可搜索)
  CREATE VIRTUAL TABLE IF NOT EXISTS memory_fts USING fts5(
    content, tags,
    content='memory_records',
    content_rowid='rowid',
    tokenize='unicode61'
  );

  -- 同步触发器
  CREATE TRIGGER IF NOT EXISTS memory_fts_ai AFTER INSERT ON memory_rec BEGIN
    INSERT INTO memory_fts(rowid, content, tags) VALUES (new.rowid, new.content,
   new.tags);
  END;
  CREATE TRIGGER IF NOT EXISTS memory_fts_ad AFTER DELETE ON memory_rec BEGIN
    INSERT INTO memory_fts(fts_idx, rowid, content, tags) VALUES('delete',
  old.rowid, old.content, old.tags);
  END;
  CREATE TRIGGER IF NOT EXISTS memory_fts_au AFTER UPDATE ON memory_rec BEGIN
    INSERT INTO memory_fts(fts_idx, rowid, content, tags) VALUES('delete',
  old.rowid, old.content, old.tags);
    INSERT INTO memory_fts(rowid, content, tags) VALUES (new.rowid, new.content,
   new.tags);
  END;

● 查到了，每个项目的写入机制很有意思。核心分 4 种模式：

  ---
  模式 A：LLM 即时提取（Mem0、Zep/Graphiti）

  消息 → 调 LLM 分析 → 提取结构化事实 → 与已有记忆对比 → ADD/UPDATE/DELETE

  Mem0 的做法：
  1. 每次 add() 时，把最新对话 + 滚动摘要 + 最近 m 条消息喂给 LLM
  2. LLM 提取出"候选记忆"（事实、偏好、重要细节）
  3. 跟已存储的 top-s 条最相似记忆对比，LLM 决定：ADD（新记）/
  UPDATE（合并更新）/ DELETE（矛盾删除）/ NOOP（已存在跳过）

  问题： 每条消息都要 LLM 调用，成本和延迟高。78.5% 的写入是 NOOP（啥也没变）。

  ---
  模式 B：Agent 自主管理（Letta/MemGPT）

  Agent 有"记忆文件"（类似操作系统）
  Agent 自己决定：这值得记住吗？
  → 调用 write_file/grep/search_files 等工具管理记忆

  Agent 像人一样主动决定什么重要、什么该忘。Letta 的发现：Agent 的 tool use 
  能力比记忆工具本身更重要——用最简单的文件系统工具跑分（74% LoCoMo）反而超过了
  Mem0 的专用记忆系统（68.5%）。

  代价： 需要 Agent 框架深度支持，不是轻量方案。

  ---
  模式 C：全量存储 + 检索时智能提取（MemMachine、Engram）

  所有对话原文存储 → 不提取 → 需要时用"检索 Agent"分析全部相关片段

  Engram 的核心哲学：在读取时投资智能，而非写入时。 因为你写入时不知道以后什么会
  重要。写入只做基本标记（类型、重要性、时间戳），检索时用 ACT-R 认知模型评分。

  MemMachine 更进一步：存储完整对话片段（不经过 LLM
  提取），然后用一个专门的"检索 Agent"在查询时自适应路由搜索策略。

  好处： 无信息丢失，写入极快（不调 LLM）。
  代价： 存储量大，检索时计算更多。

  ---
  模式 D：程序化写入（OpenDB、轻量方案）

  应用代码在特定时机主动调用 add() 写入

  最直接的方案。OpenDB（纯 SQLite FTS5，93.6%
  LongMemEval）就是用这个——应用代码决定什么时候存什么。

❯ 为什么要用一个隐藏的数字做索引？同时这个索引是干什么的？                      

● 好问题。我解释清楚。

  FTS5 的 rowid 是什么？

  在 SQLite 中，每张表都有一个隐藏的 
  rowid（除非你刻意禁用它）。不管你的主键是什么类型，SQLite 内部都会用一个 64
  位整数来标识每一行。

  memory_records 表（你看到的）：
  ┌──────────────────────────────────────┐
  │ id (TEXT PK)  │ content   │ tags     │
  ├──────────────────────────────────────┤
  │ cmt0abc...    │ 偏好 React │ ["tech"] │  ← 业务上你通过 id 查询
  │ cmt0def...    │ 用 Prisma  │ ["db"]   │
  └──────────────────────────────────────┘

  memory_records 表（SQLite 实际存储的）：
  ┌───────┬──────────────────────────────┐
  │ rowid │ id (TEXT PK)  │ content ...   │
  ├───────┼──────────────────────────────┤
  │ 1     │ cmt0abc...    │ 偏好 React .. │  ← SQLite 内部自动分配了 rowid
  │ 2     │ cmt0def...    │ 用 Prisma ... │      第一个插入 = rowid 1
  └───────┴──────────────────────────────┘

  FTS5 的全文索引又是什么？

  FTS5 不是普通的 SQLite 表，它是一个倒排索引（inverted
  index）。它的工作是：收到一个关键词，快速告诉你哪些行包含这个词。

  工作原理：
  FTS5 内部维护的数据结构（倒排索引）：

  "React"    →  出现在 rowid=1 的 content 中
  "Prisma"   →  出现在 rowid=2 的 content 中
  "TypeScript" → 出现在 rowid=1, rowid=3 的 content 中

  当你搜索 MATCH 'React' 时：
  1. FTS5 查倒排索引 → 找到 rowid=1
  2. 根据 rowid=1 回查 memory_records 表 → 取出完整内容
  3. 返回结果

  这就是为什么 FTS5 需要 rowid ——
  它是连接倒排索引和原始数据表的桥梁。倒排索引只管"这个关键词在哪些 rowid
  里"，不管你的业务 ID 是什么。

  为什么不用 TEXT id 直接做这个桥梁？

  因为整数比较比文本字符串比较快 10-100 倍。FTS5 的倒排索引查询本质上就是大量的
  ID 比较和范围扫描，用整数 rowid 可以让这些操作在 CPU 缓存级别完成。用 TEXT
  UUID 的话，每次比较都要做字符串匹配，性能会差很多。

  ---
  所以回到我们的方案：

  最简单的做法就是把 schema 改成：

  CREATE TABLE IF NOT EXISTS memory_records (
    rowid             INTEGER PRIMARY KEY AUTOINCREMENT,  -- 给 FTS5 用的数字 ID
    id                TEXT NOT NULL UNIQUE,                -- 业务 
  UUID，对外暴露
    user_id           TEXT NOT NULL,
    ...
  );

  这样 FTS5 的 content-sync 开心了（有整数 rowid 可关联），业务的 UUID
  也保留了（通过 id 字段）。或者你不想改 schema，就用手工维护 FTS
  索引的方式（每次操作同时写两张表）。

  你倾向哪种？还是说清楚后你觉得直接改 schema 最省事？

  Section 2: Code Quality Review

  D8 — Extractor JSON 解析不够健壮

  LLM 输出的 JSON 可能带各种"惊喜"：

  "当然！这是提取的记忆：\n```json\n[{\n  "action": "add",\n  "content":
  "用户偏好 React",\n  "importance": 7\n}]\n```"

  当前方案没有处理这些情况：
  - Markdown 围栏（```json）
  - 前导/后置文本（"当然！这是..."）
  - 末尾逗号
  - 字段值类型错误（importance 可能是字符串 "7"）
  - 枚举值超出范围（action: "modify" 而不是 add/update/delete/noop）

  推荐做法（借鉴 Neo4j Agent Memory 的三层策略）：

  function parseExtractorOutput(raw: string): ExtractedMemory[] {
    // 第一层：剥离 markdown 围栏
    const json = raw.replace(/```json?\n?/gi, '').replace(/```/g, '').trim();

    try {
      // 第二层：尝试严格解析
      return JSON.parse(json);
    } catch {
      // 第三层：宽松解析（修复末尾逗号、单引号等）
      const fixed = json
        .replace(/,(\s*[}\]])/g, '$1')
        .replace(/'/g, '"');
      return JSON.parse(fixed);
    }
  }

● 对，两方面都支持。这是设计上刻意做的分离：

  存储层 (Repository)          ← 谁都能调
  ├── createMemory({...})      ← 直接写入，没有任何 AI 参与

  用户点"新建记忆"   → POST /api/memory/create → createMemory()
                                        ↑
  后端代码自己分析后插入 → createMemory({ content: "...", ... })
                                        ↑
  LLM 自动提取         → extractMemories() → createMemory/update/delete()

  比如以后你想加个功能："当用户 pin
  一条消息时，自动把内容作为记忆存储"，那就是在 handlePin 里加一行
  createMemory() 的事，完全不需要经过 LLM。

  底层 createMemory() 这个函数是所有写入的统一入口，谁来调都行。
